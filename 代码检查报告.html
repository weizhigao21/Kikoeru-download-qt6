一、高严重度问题（3 项）

1

下载任务完成后内存无界增长：delegate 缩略图字典 _thumbs 永不清空

高 src/ui/qt/works_list.py:98（_thumbs）· 102（set_thumb）
问题描述

WorkCardDelegate._thumbs（url → QPixmap）只增不减：每页 20 张缩略图回调 set_thumb 写入后，翻页 / 搜索 / 切 tab 时 set_works 并不清理旧条目。ImageCacheManager 虽有 LRU，但 delegate 这层字典完全没有容量上限，与下层缓存互相独立。

影响范围

长时间使用（翻几十上百页）后，180×135 QPixmap 持续累积，内存占用线性增长，最终可达数百 MB 级；这是本项目最明确的内存泄漏点。

改进建议：在 set_works 时按新 URL 集合裁剪 _thumbs（保留当前页 + 相邻页），或给 _thumbs 加简单 LRU 上限（如 200 张）。也可以让 delegate 直接只持有当前可见窗口的图，滚动时由 ThumbnailWorker 重取（内存缓存命中，成本低）。

直接下载进度字典 _download_progress 无界增长（定义了清理函数却无人调用）

高 src/download/downloader_direct.py:10-11 · 248（clear_download_progress）
问题描述

每个直接下载文件注册一个 task_id → progress dict 条目。任务正常完成 / 失败路径（manager_poll.py:_poll_direct_task）只做状态迁移，从不清理 progress 条目；clear_download_progress 函数定义了但全项目无任何调用（已用引用追踪确认）。只有重试 / 低速重启走 _cleanup_and_reset_task 时才会清理。

影响范围

使用「直接下载」模式时，每完成一个文件就永久留下一个 dict，长期运行（7×24 小时目标场景）内存持续增长，与 README 宣称的"内存泄漏防护"目标相悖。

改进建议：任务进入终态（COMPLETED / FAILED / CANCELLED）时调用 clear_download_progress(task_id) 逐个清理（在 _poll_direct_task 的终态分支或 _on_task_completed 中）；同时把 _slow_restart_count 的残留条目一并清理。
3

下载提交前对每个文件串行发起 HEAD 网络请求，任务启动可能阻塞数十秒

高 src/download/manager_core.py:41-69 · src/download/downloader_direct.py:51-64
问题描述

_check_files_existence 在 Aria2 / 直接下载两条提交路径都会调用；对每个 本地已存在的文件，check_file_exists 会发起一次 get_remote_file_size(url) HEAD 请求（timeout=10s，串行）。一个 50 文件的列表在 CDN 响应慢时会串行阻塞数十秒；失败重试（_retry_task → _submit_task）还会再次全量检查。

影响范围

下载任务从"点击下载"到"真正开始传输"的等待明显变长；断点续传 / 重试场景每次重来一遍。虽然不阻塞 UI 线程，但拖慢下载吞吐与用户体验。

改进建议：① 用 ThreadPoolExecutor 并发执行 HEAD（上限 8-10）；② 对「本地存在且 size > 0」的文件默认信任本地大小、跳过网络校验（HEAD 仅在校验开关开启或文件大小可疑时使用）；③ 把远程大小查询结果按 URL 做内存缓存（TTL 5 分钟），重试时复用。

二、中严重度问题（12 项）

4

窗口关闭时 QThread 等待超时可能触发 "QThread: Destroyed while thread is still running" 崩溃

中 src/ui/qt/main_window.py:1096-1112（closeEvent）
问题描述

closeEvent 对数据/缩略图线程只 wait(2000)。DataWorker 的 API 请求超时 15 秒、ThumbnailWorker 可能正在下载图片，2 秒内往往退不出来。超时后 QThread 随窗口析构而销毁，工作线程仍在运行 → Qt 打印 "QThread: Destroyed while thread is still running" 并可能段错误。

影响范围

退出程序时偶发崩溃 / 挂起，尤其翻页加载中、下载中直接关窗时。

改进建议：① 增加 stop_requested 标志位，worker 循环内检查并尽快返回；② wait() 超时后不强制销毁（延迟到 worker 自然结束）；③ 或改用 QThreadPool + QRunnable，应用退出时由框架统一回收。
5

缩略图在后台单线程串行加载，翻页后首屏缩略图空白时间长

中 src/ui/qt/workers.py:129-145（ThumbnailWorker.load）
问题描述

load 对 20 个 URL 逐个循环 _load_pil_from_url，其中未缓存项是完整网络下载 + PIL 解码，全部串行。网络慢时第 1 张图也要等前序全部完成才能开始显示（实际是边下载边 emit，但一张图下载期间后续全部等待）。

影响范围

翻页 / 搜索后列表缩略图"慢慢一格格出现"，感知加载慢；CDN 单图 1-2 秒时整页要 20-40 秒。

改进建议：① 按可见行优先：先加载前 10 张再补剩余，或按"当前可见行"排序；② 用 3-5 个并发槽位（ThreadPoolExecutor 或分段线程）并行下载，注意信号回主线程顺序；③ 配合内存 LRU（已有），重绘成本可接受。

文件夹整理 / 字幕转换 / 繁简转换在全局轮询线程内同步执行，阻塞其他任务进度轮询

中 src/download/manager_poll.py:103-111（_do_pending_flatten）· 144-194（_flatten_folders）· 196-230（_convert_subtitles_and_complete）
问题描述

_do_pending_flatten 在 poll 循环线程内逐目录做文件移动 / 删除（失败重试含 sleep(2)×3），字幕 / 繁简转换线程也在该线程启动但转换本身在子线程。文件整理期间（大目录移动可能数秒），轮询循环被卡住，其余进行中任务的进度 / 低速检测 / 重试全部停摆。

影响范围

多任务并行下载时，一个任务完成触发整理会让其他任务进度暂停刷新数秒；失败重试 sleep 进一步放大。

改进建议：把 _flatten_folders 挪到独立后台线程（与字幕转换一致），或从轮询循环中拆出"整理队列"由单独 worker 消费；轮询循环只负责进度采集与任务状态。

两套功能重复的 LRU 缓存实现（_APICache vs LRUCache）

中 src/api_client.py:9-37 · src/database/cache.py:37-107
问题描述

_APICache（OrderedDict + Lock，TTL 过期）与 LRUCache（OrderedDict + RLock，带统计）核心机制相同，只是 _APICache 多了 TTL、LRUCache 多了命中率统计。两处独立维护，风格不一致（一个 time.time() 一个锁超时）。

影响范围

维护成本翻倍；修 bug 容易漏改另一处。

改进建议：合并为一个通用 TTLLRUCache（可带统计与 TTL 参数），放在 src/utils.py 或独立 src/cache.py，两处共用。
